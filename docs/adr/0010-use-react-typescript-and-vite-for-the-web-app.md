# Use React, TypeScript, and Vite for the Web App

Mellowday will develop its shared Web App as a client-side React and TypeScript application built with Vite, with the resulting static application served by the Python backend in both the Desktop Application and browser mode. This accepts a frontend build step in exchange for explicit component, state, and lifecycle boundaries across the five product areas, rather than making the growing interface maintain its own framework conventions on top of build-free ES Modules; it does not introduce a full-stack React framework, server-side rendering, or a second frontend.

The application uses hash routes so product areas and their subpages support refresh recovery, deep links, and browser navigation without adding server-side page fallbacks. Migration begins by separating the existing API, live-event, and data-conversion behavior from legacy DOM rendering, then builds complete pages in a temporary React replacement entry; the production entry changes only after the agreed compatibility boundary is met, and React islands do not share DOM ownership with the legacy renderer.

The long-lived AppShell owns routing, theme state, and one application-wide live-event connection. Route pages subscribe to that connection and own only their page-specific loading, cancellation, and polling lifecycles, so navigation neither recreates the live connection nor leaves diagnostics and management polling active after its page closes. Migration preserves backend request and response contracts, live-event semantics, confirmation protocols, existing local data, browser mode, user-visible behavior, and semantically equivalent accessible names; legacy DOM identifiers, CSS classes, internal functions, and exact incidental status wording are not compatibility contracts, and the legacy entry is removed after those behavior boundaries pass.

Theme selection and the Minimal theme's editable values remain per-client presentation preferences in one versioned local-storage record. Sky is the default theme; missing, invalid, or unmigratable preferences fall back to valid defaults. The four decorative themes are fixed, while Minimal derives its palette from an accent hue and background brightness, never loads decorative assets, and can reset its editable values without changing the selected theme. Settings Appearance is the single appearance-management surface and reuses the same application-owned appearance state and component behavior.

The five reference images define visual intent, the accepted A+C prototype verdict defines structure and verified size evidence, and prototype measurements are candidates rather than production CSS. The production specification defines semantic visual tokens afresh instead of copying prototype styles. Minimal remains a light theme with background lightness constrained to approximately 88–100%, automatic accessible foreground and control contrast, and optional subtle CSS-only haze without decorative DOM or asset requests. All themes preserve component geometry, content width, and body typography metrics; decorative themes may vary only limited brand or display typography, while Minimal uses the base type treatment.

Production promotes exactly the matching emblem WebP, corner WebP, and motif SVG for each of Sky, Sakura, Mint, and Night. Reference screenshots, editable source images, and prototype copies remain documentation or throwaway evidence and do not enter runtime packages; Minimal has no decorative runtime asset. The Vite build produces the complete frontend artifact tree before Python packaging, and the wheel recursively includes only runtime output rather than frontend source, prototypes, or design documentation. Distribution tests assert the entry, generated JavaScript and CSS, dynamic chunks, and all twelve promoted theme assets instead of treating one root HTML file as sufficient evidence.

The frontend verification boundary includes TypeScript checking; focused unit tests for services, theme derivation, and route state; Playwright behavior tests for routing, the persistent live connection, page-specific polling cleanup, keyboard and focus behavior, and target viewports; and a small representative screenshot set rather than a pixel baseline for every theme and size. Existing browser tests migrate to semantic behavior assertions under the compatibility boundary, while real Windows scaling remains a Desktop Shell acceptance check.

Interactive text, controls, focus indicators, and states meet WCAG 2.2 AA contrast. Settings Appearance uses ordinary page controls rather than menu semantics inappropriate for theme radios and sliders. The narrow recent-conversation drawer is modal, makes background content unavailable, contains focus until dismissal, and restores focus to its trigger. All operations remain keyboard reachable with visible focus; document order proceeds through title bar, product navigation, main content, and composer; new conversation and proactive content uses restrained live-region announcements without rereading the transcript. The first version adds no global custom keyboard shortcuts beyond the already defined local composer and overlay behavior.
