## 1. 对照设计（为什么这样设计）

| 维度 | 做法 |
|---|---|
| 三个条件 | `off`：没有任何规划规则（对照）；`fixed`：人工写死的规划技能（同一条要求）；`learned`：真实纠正经产品路径学习出的规则 |
| 模型参数 | 三组读同一份运行配置（同一模型、端点、`thinking`、`max_turns`），并逐字比对配置一致（报告字段 `same_model_configuration`） |
| 业务初始数据 | 三组写入完全相同的数据：`dev` 案例 = 次日固定日程「每日站会 09:30」+ 6 条待办；`holdout` 案例 = 下周一固定日程「客户复盘会 14:00」+ 4 条待办；另有 2 条用户事实 |
| 开发 / 保留案例 | `dev` 请求「帮我规划一下明天要做的事。」= 纠正所针对的那次请求；`holdout` 请求「帮我规划一下下周一的安排。」= 不同日期、不同记录，**在纠正轮之后才写入**，学习侧与人工技能都无法照抄 |
| 抽样 | 每条件 × 每案例 3 个全新会话（分母写在报告的每个 `metrics` 与 `of` 字段里） |
| 度量 | 「规则遵守」= 固定日程 + 重点任务两个小节、真实日程被写入计划、重点任务恰为 3 条、至少 3 条真实待办被采用；同时记录规则文本是否真的进入请求（`rule_loaded`）与经哪条通道（技能 / 事实） |
| 不预填结论 | 脚本只统计与记录，不计算、不打印、不声明任何提升比例；小样本按小样本报告 |

技能条件如何建立：
- `off`：不写入任何技能（技能列表为空、事实库无规则）；
- `fixed`：`create_skill_file` 写入人工技能「固定规划格式」，正文只描述规则本身，不含任何本机记录；
- `learned`：`PLAN_ASK` → 明确纠正「以后必须先列固定日程、只排三个重点任务」→ 确认 → 落盘；随后把该技能正文的最后一条要求句作为「只可能来自正文」的探针。

## 4. 限制与需要读者注意的地方

- **小样本**：每格 3 个样本，只能用于确认方向与结构，不能当作效果量；分母已写在每个 `of` 字段里。本对照也**不**回答「学习到的规则是否比人工技能更好」——两者在开发案例与保留案例上的差异都在抽样噪声范围内，脚本因此只报告计数。
- **投递通道**：`learned` 条件的规则可能同时经「技能」与「事实库」两条通道到达模型（事实通道由运行时每轮注入）。报告为每个样本记录 `delivery_channels`，并把「正文探针是否出现在请求里」与「系统提示是否广告该技能」分开——后者恒为真，不能当作规则被加载的证据。
- **规则停用不在本对照范围内**：停用条件受事实通道污染，已在核心演示里判为作废（见 `P3-P4-core-demo.md` 第 3 节），其结论由 T5 重跑（t11）给出。
- **并发改动**：P5 与其它单元的运行重叠时，`code.workspace_unchanged_during_the_run` 会判 inconclusive，报告里的工作区指纹只对应运行开始那一刻。
- **未纳入**：长结果经 ref 取回（t10 的 HTTP 路由）未进入本对照；主动问候/每日回顾（P6）不在本轮。
